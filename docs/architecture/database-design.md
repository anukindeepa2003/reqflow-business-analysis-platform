# Initial Database Design

## Status

Phase 3 implements the PostgreSQL `projects` and `requirements` tables, their enum types, integrity constraints, relationships, supporting indexes, and reviewed Prisma migrations. Acceptance criterion, test case, traceability, and change-history entities remain planned and are not represented as implemented.

## Conventions

- Every application primary key is a UUID generated independently of display identifiers.
- Foreign keys are explicit and use PostgreSQL referential integrity.
- Timestamps are stored as UTC-capable `timestamptz` values.
- Records that are displayed externally will use stable readable identifiers where needed.
- Indexes will follow actual query patterns; foreign keys and common filters are initial candidates.

## Implemented and planned entities

### Project

- **Implementation:** Implemented in migration `20260927133517_init_project_management`.
- **Primary key:** UUID `id`, generated by Prisma.
- **Attributes:** required trimmed `name` (2–120 characters), optional `description` (up to 2,000 characters), `status`, persistent `next_requirement_number`, `created_at`, and `updated_at`.
- **Status values:** `PLANNING`, `ACTIVE`, `ON_HOLD`, `COMPLETED`, and `ARCHIVED`. These are internal tracking labels, not stakeholder approvals.
- **Integrity:** PostgreSQL check constraints protect name formatting and field lengths in addition to API-level Zod validation.
- **Index:** `(status, updated_at DESC)` supports future status-filtered recent-project queries.
- **Relationships:** One Project owns many implemented Requirements. Test cases remain planned.

### Requirement

- **Implementation:** Implemented in migration `20261102035133_add_requirement_management`.
- **Primary key:** UUID `id`, generated independently from the readable identifier.
- **Foreign key:** `project_id -> projects.id` with `ON DELETE CASCADE`.
- **Attributes:** positive project-scoped `sequence_number`, required trimmed `title` (2–200 characters), required trimmed `description` (10–5,000 characters), `type`, `priority`, `status`, and timestamps.
- **Type values:** `FUNCTIONAL` and `NON_FUNCTIONAL`.
- **MoSCoW priority values:** `MUST`, `SHOULD`, `COULD`, and `WONT` for this release.
- **Status values:** `DRAFT`, `READY`, `IN_PROGRESS`, `IMPLEMENTED`, and `DEFERRED`. Statuses are simulated internal tracking labels, not stakeholder approvals.
- **Integrity and indexes:** `(project_id, sequence_number)` is unique; project/status/date, project/type, and project/priority indexes support current list and filter patterns.
- **Relationships:** Belongs to exactly one implemented Project. Acceptance criteria, change records, and test links remain planned.

### AcceptanceCriterion

- **Primary key:** UUID `id`
- **Foreign key:** `requirementId -> Requirement.id`
- **Purpose:** Captures a verifiable condition for a requirement.
- **Likely attributes:** description, position/order, timestamps.
- **Relationships:** Belongs to exactly one requirement.

### TestCase

- **Primary key:** UUID `id`
- **Foreign key:** `projectId -> Project.id`
- **Purpose:** Describes a test that can provide evidence for one or more requirements.
- **Likely attributes:** display key/sequence, title, preconditions, steps, expected result, status, timestamps.
- **Relationships:** Belongs to a project; links to many requirements.

### RequirementTestCase

- **Primary key:** Either a UUID or a documented composite key; not finalized.
- **Foreign keys:** `requirementId -> Requirement.id`, `testCaseId -> TestCase.id`.
- **Purpose:** Many-to-many junction between requirements and test cases.
- **Required constraint:** A requirement/test pair must be unique.
- **Required invariant:** Both linked records must belong to the same project.

The same-project invariant cannot be safely delegated only to the UI. The service will verify it within the write transaction. During schema implementation, the team will evaluate whether denormalizing `projectId` into the junction plus composite foreign keys provides worthwhile database-level enforcement without creating unnecessary update complexity.

### RequirementChange

- **Primary key:** UUID `id`
- **Foreign key:** `requirementId -> Requirement.id`
- **Purpose:** Provides a basic audit trail of material requirement changes.
- **Likely attributes:** field/change summary, previous value, new value, reason (if required), changed timestamp.
- **Relationships:** Belongs to exactly one requirement.

Because the MVP is single-user without authentication, a trustworthy user identity cannot be recorded. The schema must not invent an actor. Actor information can be added when identity is implemented.

## Relationship summary

```text
Project 1 ----- * Requirement 1 ----- * AcceptanceCriterion
   |                  |
   |                  *
   |          RequirementTestCase
   |                  *
   * ----- * TestCase

Requirement 1 ----- * RequirementChange
```

## Readable identifiers

UUIDs remain the persistent keys. Requirements expose `REQ-` plus their persisted, project-scoped sequence number padded to four digits, for example `REQ-0001`. Project creation initializes `next_requirement_number` to 1. Requirement creation atomically increments that counter and stores the allocated value; deletion does not decrement it. Consequently, identifiers are not derived from row counts, are not reused after deletion, and do not change when requirement text changes. Test-case identifier allocation remains unfinalized.

## Transaction boundaries

- Requirement creation increments the owning Project counter and inserts the Requirement inside one short Prisma transaction.
- Updating a requirement and inserting its future `RequirementChange` records must occur in one database transaction once history is implemented.
- Creating a requirement/test link must validate project ownership and create the junction record within one transaction where required to avoid time-of-check/time-of-use inconsistencies.
- Multi-record deletes must either complete fully or roll back.

## Data integrity considerations

- Required fields should be non-null at the database level.
- Unique constraints should prevent duplicate project-scoped display keys and duplicate traceability links.
- Foreign keys should prevent orphan acceptance criteria, traceability links, and change records.
- Zod validation will enforce input shape and supported enum values before persistence.
- Services will enforce rules that depend on multiple records; supported database constraints will provide a second line of defense.
- Length limits and normalization rules will be defined before migrations, not inferred only from UI controls.

## Project deletion policy

The implemented policy is an explicit, confirmed hard delete for local test/portfolio data. The UI names the project and warns that deletion is permanent; the API exposes only an individual `DELETE /api/projects/:projectId` operation and no broad bulk-delete endpoint. PostgreSQL now cascades Project deletion to its Requirements through the implemented foreign key.

Future acceptance criteria, test cases, traceability links, and change records must define and test their own cascade/restrict behavior before they are added. This hard-delete policy is not automatically suitable for a regulated or collaborative system, where archival, retention, backup, and audit requirements would need stakeholder and legal input.

## Decisions not finalized

- Exact fields, lengths, and optionality for entities other than Project and Requirement
- Test case status vocabulary and step representation
- Junction-table primary key strategy and database enforcement of project equality
- Test-case sequence allocation and readable-key prefixes
- Which changes qualify for history and how structured the history payload should be
- Whether optimistic concurrency/version fields are needed
- Retention, archival, backup, and recovery requirements beyond the local MVP
